Code Review: Refatoração de Controller Spring

❌ Antes (Código Original)

// Package and imports omitted for brevity.

@RestController
@RequestMapping("/persons")
public class PersonController {

    @Autowired
    public PersonRepository personRepository;

    @GetMapping("/person")
    public Person getPersonById(@RequestParam String id) {
        List<Person> persons = personRepository.findAll();
        Person person = null;
        for (Person p : persons) {
            if (p.getId().equals(Long.parseLong(id))) {
                person = p;
                break;
            }
        }
        if (person == null) {
            return null;
        }
        calculateSalary(person);
        return person;
    }

    public void calculateSalary(Person person) {
        Double salary = 0.0;
        for (Invoice invoice : person.getInvoices()) {
            switch (invoice.getInvoiceType()) {
                case "FATURADO":
                    salary += invoice.getAmount();
                    break;
                case "PENDENTE":
                    break;
            }
        }
        person.setSalary(salary);
    }
}

✅ Depois (Código Melhorado)

@RestController
@RequestMapping("/persons")
public class PersonController {

    private final PersonService personService;

    // Injeção de dependência via construtor
    public PersonController(PersonService personService) {
        this.personService = personService;
    }

    // Padrão REST com @PathVariable
    @GetMapping("/{id}")
    public ResponseEntity<PersonDTO> getPersonById(@PathVariable Long id) {
        return personService.findById(id)
                .map(ResponseEntity::ok)
                .orElse(ResponseEntity.notFound().build());
    }
}

// --- Separação em Camadas: Service ---
@Service
public class PersonService {
    
    private final PersonRepository personRepository;

    public PersonService(PersonRepository personRepository) {
        this.personRepository = personRepository;
    }

    public Optional<PersonDTO> findById(Long id) {
        // Delegação correta ao banco e conversão para DTO
        return personRepository.findById(id).map(PersonDTO::new);
    }
}

// --- DTO e Imutabilidade ---
public class PersonDTO {
    private final Long id;
    private final BigDecimal salary;

    public PersonDTO(Person person) {
        this.id = person.getId();
        // Cálculo via Streams com Enum e BigDecimal
        this.salary = person.getInvoices().stream()
            .filter(Invoice::isFaturado)
            .map(Invoice::getAmount) // Retorna BigDecimal
            .reduce(BigDecimal.ZERO, BigDecimal::add);
    }
    
    // Getters omitidos...
}

Explicação das Melhorias

Problema no código original Melhoria aplicada
Tudo em uma única camada, com o repository usado direto no controller. Separar em camadas: O controller agora chama um Service, que por sua vez utiliza o Repository.
findAll seguido de um for comparando IDs. Usar findById do Spring Data JPA. Trazer a coleção inteira para a memória para filtrar um item é considerado um erro grave. Delega-se a busca diretamente ao banco.
Injeção com @Autowired em atributo public. Injeção por construtor com atributo private final. Facilita os testes unitários e remove a dependência direta de reflection do framework.
ID recebido via @RequestParam (na query string). Usar /{id} no caminho com @PathVariable, respeitando melhor as convenções arquiteturais REST.
ID recebido como String e convertido com Long.parseLong(). Declarar o parâmetro já tipado como Long, deixando o Spring cuidar do binding de tipos.
Verificação de null no resultado manual. Tratar o Optional retornado pelo findById utilizando map, isPresent ou orElse.
Retorno do objeto direto, podendo ser null. Retornar ResponseEntity com o status HTTP adequado. Retorna 200 OK se achar, ou 404 Not Found quando a pessoa não existir.
Cálculo do salário em um método público do controller. Mover a responsabilidade de cálculo para fora (ex: DTO ou Service). No código refatorado, o cálculo ocorre no momento da construção do PersonDTO.
Uso de double para valores monetários. Usar BigDecimal. Tipos flutuantes perdem precisão com valores decimais. BigDecimal resolve o problema de precisão monetária gerando novos objetos imutáveis.
Comparação de status com String e switch desnecessário. Criar um Enum e usar Streams API com filter (ex: Invoice::isFaturado). O cálculo se reduz a uma linha legível.
Entidade de banco de dados exposta diretamente na resposta. Retornar um DTO (PersonDTO), protegendo o modelo do banco de dados e evitando alterações acidentais de estado (mutabilidade) no objeto da entidade.

💡 Notas Arquiteturais da Revisão

Por que BigDecimal? Valores de ponto flutuante (IEEE 754) trabalham com aproximações. Em sistemas financeiros, essas aproximações geram diferenças em centavos que comprometem o sistema. BigDecimal garante precisão absoluta para dinheiro.

Por que Streams? O uso da Streams API combinada com Method References (::) favorece uma leitura semântica do que está sendo feito (declaração) em vez de como está sendo feito (imperativo). A lazy evaluation também delega otimizações de execução para a JVM.

Imutabilidade e DTOs: O método original calculateSalary(person) alterava o estado do objeto. Mover os dados para um DTO de resposta onde atributos extras (como o salário calculado) são injetados sem alterar a entidade raiz favorece operações thread-safe e a imutabilidade.
